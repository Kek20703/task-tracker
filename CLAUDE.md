# Task Tracker — правила работы

Учебный проект по ТЗ: https://zhukovsd.github.io/java-backend-learning-course/projects/task-tracker/

## План

План разработки, статус этапов, принятые решения и долги — в [docs/PLAN.md](docs/PLAN.md).
Полная постановка этапа — в `docs/specs/NN-slug.md` по шаблону `docs/specs/TEMPLATE.md`:
её готовит агент по общим очертаниям владельца, владелец утверждает до начала кода.
В начале сессии прочитать план и продолжать с этапа со статусом `следующий` или `в работе`.
Статус этапа обновляется в том же PR, который этап закрывает.

## Структура

Монорепозиторий: четыре независимых Gradle-проекта по папкам (`task-tracker-backend`,
`task-tracker-email-sender`, `task-tracker-summarization-server`, `task-tracker-scheduler`)
и общий `docker-compose.yml` в корне. Фронтенда нет — вместо него `.http`-коллекция.

## Сборка

- Java 17. В PATH её нет: перед запуском Gradle выставлять `JAVA_HOME` на JDK из `~/.jdks/ms-17*`.
- Собирать через Gradle wrapper (`./gradlew`) внутри папки сервиса.
- `./gradlew check` — тесты и проверка покрытия JaCoCo (порог 70% строк). Отчёт —
  `build/reports/jacoco/test/html/index.html`.
- Имя пользователя Windows содержит кириллицу, из-за чего Java падает с
  `Unable to establish loopback connection`. Перед запуском Gradle из терминала выставлять
  `JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=C:/Windows/Temp`.
- Интеграционные тесты поднимают Postgres через Testcontainers — нужен запущенный Docker.

## Миграции БД

- Liquibase, формат XML. Владелец схемы — `task-tracker-backend`.
- Мастер-файл: `src/main/resources/db/changelog/db.changelog-master.xml`, миграции —
  отдельными файлами в `changes/` с номером по порядку (`002-...xml`).
- Миграцию, попавшую в `dev`, не редактировать — только добавлять новую.

## Архитектурные тесты

В каждом сервисе есть `ArchitectureTest` (ArchUnit) — он проверяет структуру кода и запускается
вместе с остальными тестами. Правила:

- Пакеты по слоям: `controller`, `service`, `repository`, `entity`, `dto`, `exception`,
  `validation`, `config`, `security`. Класс вне этих пакетов роняет сборку.
- Зависимости только сверху вниз: контроллер → сервис → репозиторий. К репозиториям ходят
  только сервисы — `config` и `security` тоже работают с данными через сервис.
- JPA-сущности не выходят из сервисного слоя: от `entity` зависят только `service` и
  `repository`. Контроллеры, `security` и `config` получают от сервисов DTO.
- Сущности и DTO не зависят от остальных слоёв; циклов между пакетами нет.
- Внедрение зависимостей только через конструктор; вместо `System.out` — логгер;
  вместо `RuntimeException` — свой тип исключения.

Если тест падает — исправлять код, а не ослаблять правило. Менять сами правила можно только
по согласованию с владельцем репозитория. Новый сервис начинается с копии этого набора правил.

## Git-процесс

- Ветки: `master` (стабильная), `dev` (интеграционная), `feature/<кратко-о-правке>` от `dev`.
- Прямых коммитов в `master` и `dev` нет. Каждая правка — отдельная ветка и PR в `dev`.
  Один PR — один этап плана или одна правка.
- После завершения этапа плана — PR `dev` → `master`.
- Цикл работы над этапом:
  1. постановка: владелец даёт общие очертания; агент пишет `docs/specs/NN-slug.md`, задаёт вопросы;
     владелец утверждает постановку до начала кода;
  2. исполнитель: ветка от `dev`, план шагов, код, тесты, миграции, `./gradlew check`, PR в `dev`;
  3. ревьюер: субагент `reviewer` читает дифф PR, постановку этапа, `ArchitectureTest.java`,
     `docs/PLAN.md` и этот файл, оставляет замечания по severity: `blocker`, `major`, `minor`, `nit`
     и вердикт «можно сливать» / «нельзя сливать»; код не меняет;
  4. итерация: исполнитель правит `blocker` и `major` в той же ветке, ревьюер перепроверяет;
  5. слияние: когда `blocker` и `major` закрыты, новых `blocker`/`major` нет, локальные проверки
     зелёные и критерии готовности выполнены, агент сливает PR `feature → dev` обычным merge-коммитом
     и удаляет ветку. `minor`/`nit` не блокируют: они фиксируются в «Долгах» или явно принимаются.
     Затем агент проверяет, что в `master..dev` только merge-коммиты (нет прямых коммитов), открывает
     и сливает релизный PR `dev → master` тем же способом. Отдельное ревью релизного PR не нужно:
     его изменения уже проверены в PR этапа.
- Ревью субагентом `reviewer` обязательно для любого PR с изменениями; релизный PR `dev → master`
  не ревьюится повторно, если содержит только уже проверенные merge-коммиты. Для мелких правок
  действуют шаги 2–5 цикла в применимой части, кроме обновления статуса этапа в `docs/PLAN.md`.
- Этап берётся в работу командой `/stage` (аргумент — номер этапа) или вручную по тому же порядку.
- Коммиты и PR оформляются только от имени владельца репозитория: никаких строк
  `Co-Authored-By: Claude` в коммитах и подписей «Generated with Claude Code» в PR и комментариях.
- Сообщения коммитов и описания PR — на русском.
- Секреты (`.env`, ключи, пароли SMTP) в репозиторий не попадают; образец — `.env.example`.
