# План разработки

ТЗ: https://zhukovsd.github.io/java-backend-learning-course/projects/task-tracker/

Этот файл — единственный источник правды о том, что сделано и что дальше. Его читает человек
и агент в начале каждой сессии. Правила работы (git-процесс, сборка, архитектурные тесты) —
в [CLAUDE.md](../CLAUDE.md).

## Как вести этот файл

- Статус этапа меняется в том же PR, который этот этап закрывает.
- Статусы: `сделано`, `в работе` (с именем ветки), `следующий`, `—`.
- Полная постановка этапа — отдельный файл `docs/specs/NN-slug.md` по шаблону
  [specs/TEMPLATE.md](specs/TEMPLATE.md). В таблице статуса — ссылка на постановку.
- Постановку готовит агент по общим очертаниям владельца; владелец утверждает её до начала кода.
  Утверждение фиксируется в файле: `Статус постановки: утверждена` и дата.
- Решение, принятое по ходу работы, дописывается в «Принятые решения».
- Отложенное на потом дописывается в «Долги» с указанием этапа, на котором его нужно закрыть;
  закрытый долг удаляется.

## Этапы

### Этап 4. Backend: задачи

- **База:** миграция Liquibase `002` с таблицей `tasks` — заголовок, описание, владелец
  (внешний ключ на `users`), статус, время выполнения `completed_at`.
- **API:**
  - `GET /tasks` — список задач текущего пользователя.
  - `POST /tasks` — создание.
  - `PATCH /tasks/{id}` — частичное обновление заголовка, описания или статуса;
    `completed_at` выставляет сервер.
  - Статус задачи — `TODO` или `DONE`. При переходе в `DONE` сервер ставит `completed_at = now()`,
    при возврате в `TODO` обнуляет. Новая задача создаётся в `TODO`.
  - `DELETE /tasks/{id}` — удаление.
- **Доступ:** чужая задача отвечает 404, а не 403, чтобы не раскрывать её существование.
- **Проверка:** интеграционные тесты, включая доступ к чужим задачам; `.http`-коллекция.

### Этап 5. Email sender

- **Сервис:** новый `task-tracker-email-sender` на Spring Kafka и Spring Mail, со своим набором
  архитектурных тестов.
- **Kafka:** создаёт топик `EMAIL_SENDING_TASKS` и читает из него сообщения с адресом,
  заголовком и текстом письма.
- **Почта:** локально письма уходят в Mailpit, на проде — через SMTP Unisender из переменных окружения.
- **Сбои:** повторные попытки и отдельный топик для сообщений, которые не удалось отправить.
- **Проверка:** тест с Kafka в Testcontainers.

### Этап 6. Приветственное письмо

Полная постановка — в [specs/06-welcome-email.md](specs/06-welcome-email.md). Кратко: backend после
успешной регистрации пишет письмо в `EMAIL_SENDING_TASKS`; регистрация не падает и не задерживается,
если Kafka недоступна; отправка идёт после фиксации транзакции; DTO и формат сообщения проверяются
тестом с обеих сторон.

### Этап 7. Summarization-сервис

Полная постановка — в [specs/07-summarization.md](specs/07-summarization.md).

- **Сервис:** новый `task-tracker-summarization-server`.
- **Kafka RPC:** получает запрос с задачами пользователя за период, отвечает отчётом в топик ответов.
- **LLM:** прямой HTTP-вызов OpenAI-совместимого API без SDK; адрес, модель и ключ — из
  переменных окружения. Системный промпт с форматом и примерами.
- **Своя база:** отдельная база `summarization` в том же экземпляре Postgres (второй контейнер
  не нужен), свои миграции Liquibase. Базу создаёт init-скрипт Postgres в compose; на уже
  существующем томе её нужно создать один раз вручную — это описать в README.
- **Без ключа:** режим-заглушка, чтобы цепочка работала локально. Сбой или таймаут LLM даёт
  простой отчёт по шаблону, а не потерю письма.
- **Нужно от владельца:** ключ и адрес LLM API.

### Этап 8. Scheduler

- **Сервис:** новый `task-tracker-scheduler` на Spring Scheduler и Spring Kafka.
- **Расписание:** каждую полночь находит пользователей, у которых за сутки есть сделанные
  задачи или остались несделанные. Часовой пояс задаётся переменной окружения, по умолчанию UTC.
  «Сутки» — предыдущий календарный день в этом поясе: задачи с `completed_at` от полуночи до полуночи.
- **Данные:** читает ту же Postgres напрямую, только на чтение.
- **Оркестрация:** для каждого пользователя запрашивает отчёт по Kafka RPC и отправляет письмо
  в `EMAIL_SENDING_TASKS`.
- **Проверка:** сквозной прогон всей цепочки с ручным запуском расписания.

### Этап 9. Docker-образы, CI/CD, деплой

- **Dockerfile** на каждый из четырёх сервисов, двухстадийный: сборка jar на JDK, запуск на
  лёгком образе с JRE.
- **Compose:** полный стек — четыре сервиса, Postgres и Kafka, с ожиданием готовности зависимостей.
- **CI на PR:** GitHub Actions гоняет тесты всех сервисов, включая архитектурные, и проверку
  покрытия (`./gradlew check`, порог 70% строк).
- **CD:** при пуше в `master` образы собираются и публикуются в Docker Hub. Логин и токен
  Docker Hub хранятся в секретах GitHub, не в репозитории.
- **Деплой:** compose-файл для сервера и инструкция. По ТЗ приложение открывается по
  `http://$server_ip`, поэтому на сервере backend публикуется на 80-м порту (`80:8080`).
- **Нужно от владельца:** аккаунт Docker Hub, доступы SMTP Unisender, сервер на Linux.

## Принятые решения

- **Структура:** один репозиторий, четыре независимых Gradle-проекта по папкам, общий `docker-compose.yml`.
- **Стек:** Java 17, Spring Boot 4.1, Gradle, Postgres 18, Kafka 4 (KRaft), Liquibase с XML.
- **Persistence:** Spring Data JDBC без JPA/Hibernate; первичные ключи — UUIDv7, новая запись
  отличается по `@Version`, `created_at` заполняется аудитом Spring Data JDBC.
- **Фронтенда нет:** только REST API и `.http`-коллекция. SPA — возможный отдельный этап после девятого.
- **Swagger UI** (springdoc) на `/swagger-ui.html` — для ручной проверки API, открыт без авторизации,
  как и описание `/v3/api-docs`. Выключается переменной `SWAGGER_ENABLED=false`; перед деплоем
  (этап 9) решить, оставлять ли его включённым на сервере.
- **LLM:** OpenAI-совместимый API, настройки через переменные окружения.
- **Схемой БД владеет backend;** scheduler читает ту же базу напрямую, только на чтение.
- **Mailpit** как локальный SMTP — добавка сверх ТЗ, чтобы проверять письма без реальных доступов.
- **JWT:** только access token на 24 часа, без refresh; передаётся в заголовке
  `Authorization: Bearer ...`. Фильтр не ходит в базу.
- **Logout:** серверного метода нет. Сессий нет, токен нигде не хранится — выход означает, что
  клиент забывает токен; до истечения срока он остаётся действительным.
- **Ошибки API:** всегда `{"message": "..."}`, тексты только свои.
- **API задач:** `PATCH` частичный — отсутствующее или `null` поле не меняется, описание
  очищается пустой строкой. Чужая задача отвечает 404, как несуществующая. Каждая операция
  с задачами сначала проверяет, что пользователь из токена ещё существует. `PATCH` и `DELETE`
  блокируют строку задачи (`SELECT ... FOR UPDATE`), чтобы одновременные автосохранения не
  затирали друг друга. Символ U+0000 во входных строках отклоняется на валидации — Postgres его не хранит.
- **Секреты** (`POSTGRES_PASSWORD`, `JWT_SECRET`) — только из окружения; рабочих значений по
  умолчанию нет, без них сервис не стартует.
- **Контракт письма:** сообщение в `EMAIL_SENDING_TASKS` — JSON с DTO `EmailMessage`
  (`to`, `subject`, `text`). DTO объявлен в email-sender; на этапе 6 такой же появится в backend.
  Тип для потребителя берётся из настройки, а не из заголовков Kafka: отправитель — другой
  сервис, и его класса здесь нет. Producer в backend на этапе 6 тоже должен слать JSON
  без заголовков типа.
- **Недоставленные письма:** при сбое отправки сервис делает до трёх попыток с паузой, затем
  перекладывает сообщение в `EMAIL_SENDING_TASKS.DLT` — очередь не блокируется «отравленной»
  записью. Число попыток и пауза настраиваются.
- **Архитектурные тесты:** новый сервис получил тот же набор правил, что и backend. В нём нет
  слоёв controller, repository и entity, поэтому правила для них помечены `allowEmptyShould(true)`,
  а типы, которых нет в зависимостях сервиса (`@Entity` и т.п.), в правилах заданы по имени.
- **Покрытие тестами:** JaCoCo подключён в каждом сервисе. Порог — не ниже 70% строк, проверяется
  задачей `check` (в CI на этапе 9 её нужно гонять вместо одного `test`). Покрытие считается по всем
  тестам из `test`, включая интеграционные; класс запуска приложения исключён как boilerplate.
  Отчёт — `build/reports/jacoco/test/html/index.html`.
- **Процесс:** постановку этапа агент готовит в `docs/specs/NN-slug.md` по шаблону, владелец
  утверждает её до начала кода. Этап ведётся командой `/stage`; ревью любого PR с изменениями делает
  субагент `reviewer`. Когда `blocker` и `major` закрыты, новых `blocker`/`major` нет, локальные
  проверки зелёные и критерии готовности выполнены, агент сливает PR `feature → dev`, затем
  `dev → master` обычным merge-коммитом. `minor`/`nit` не блокируют и фиксируются в «Долгах».
  Релизный PR `dev → master` не ревьюится повторно, если в нём только уже проверенные merge-коммиты.

## Долги

- **Без срока.** Гарантированная доставка приветственного письма: outbox или повторная публикация,
  если Kafka была недоступна. Сейчас письмо может потеряться. Из постановки этапа 6.
- **Этап 9.** За обратным прокси задать `server.forward-headers-strategy`, иначе Swagger покажет
  адрес сервера `localhost:8080`. Из ревью PR #7.
- **Этап 9.** Адреса Postgres, Kafka и SMTP для сервисов в контейнерах задавать переменными
  окружения (`SPRING_DATASOURCE_URL` и т.п.): `localhost` из контейнера не сработает. Из ревью PR #1.
- **Без срока.** Вход делает два запроса в базу; убрать нельзя без цикла `service ↔ security`.
  Ограничения частоты попыток входа нет. Время ответа для существующего и несуществующего
  email тестом не измеряется. Из ревью PR #3.
